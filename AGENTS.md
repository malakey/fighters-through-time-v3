## Product identity and non-negotiable pillars

`Fighters Through Time` is a 2D game that combines side-scrolling action-adventure gameplay with a platform-fighter mode. The nine playable characters are historical figures whose exaggerated abilities are manifestations of humanity's collective memory, called Temporal Resonance.

Core design contracts:

- An ability must make sense in both modes. The same move used for Story Mode combat or a puzzle should translate naturally to Fighter Mode.
- Combat uses standard HP, not a Smash-style accumulating knockback percentage. At 0 HP a fighter is knocked out. In Fighter Mode, falling through the bottom blast zone also costs one stock; the sides and top are solid boundaries.
- Story progression and the Temporal Resonance Grid affect Story Mode only. Fighter Mode remains competitively normalized.
- All nine characters are available from the start in the initial build. Character unlocking is a later balance/content phase.
- A campaign save locks the selected character for the whole playthrough; there is no mid-campaign character swapping.
- The initial Fighter Mode scope is 1v1 only: local shared-screen/LAN and online rollback. Four-player free-for-all and 2v2 are post-launch work and must not be added during initial development.
- Delay-based online combat is not acceptable. The intended final online implementation is deterministic GGPO-style rollback.
- Initial builds are English-only but must be localization-ready from day one. User-visible strings use translation keys, not hardcoded English.
- Alternate costumes, cosmetic items, full-match replays, detailed post-match stat sheets, online account/profile systems, and Training Mode are outside the initial scope unless the user explicitly reprioritizes them.

## Narrative and mode context

An overload at the Library of Alexandria fractures history, opens Chronal Rifts, displaces the selected hero, and grants Temporal Resonance powers. The Chrono-Resistance, led by Commander Sarah, operates from a hijacked Archive Time-Ship that serves as the Story Mode hub.

The campaign follows only the player's locked-in historical figure and the Chrono-Resistance crew. Other playable roster characters do not appear as hub NPCs or campaign companions. Fighter Mode is narratively framed as sparring in the Time-Ship's Temporal Arena.

## Technology and runtime targets

- Engine in the current repository: Godot .NET 4.7.1 (`Godot.NET.Sdk/4.7.1`). The GDD's minimum is Godot 4.4+.
- Language/runtime: C# on .NET 10 (`net10.0`, SDK 10.0.302 pinned by `global.json`). Root namespace: `FTT`. Migrated from .NET 8 on 2026-08-06; Godot 4.7.1 loads the `net10.0` assembly and the full suite passes. `design-godot.md` Section 12 still says .NET 8 — the project file is authoritative.
- Current package/runtime dependencies: `K4os.Compression.LZ4` 1.3.8, Klotho's `Newtonsoft.Json` 13.0.4 and `LiteNetLib` 2.1.4 runtime dependencies, plus Debug-only GdUnit4 test packages.
- Current renderer setting: `gl_compatibility`, using Godot's 2D `CanvasItem` stack. The intended art pipeline uses `Light2D`, `CanvasModulate`, `LightOccluder2D`, normal maps, and custom `CanvasItem` shaders.
- Target platforms: Windows, macOS, Linux/SteamOS, with Steam Deck performance in mind.
- Simulation and presentation target: locked 60 FPS / 60 Hz physics.
- Reference resolution: 1920×1080. `project.godot` and `ViewportEnforcer` use fixed `keep` aspect behavior with black letterbox/pillarbox clear areas.
- Performance target: 16.67 ms per frame, no gameplay-time GC spikes, at most 4 GB runtime RAM, roughly 150 draw batches, 150,000 visible vertices, 60 active `AnimatedSprite2D` nodes, and 500 active particles. Pool short-lived gameplay objects.

## Scene architecture and flow

- Main scene: `res://scenes/menus/MainMenu.tscn`.
- Scene changes use single-scene replacement through `GameManager.LoadScene`, `ResourceLoader.LoadThreadedRequest`, and `SceneTree.ChangeSceneToPacked`.
- `GameManager` builds a themed `LoadingScreen` per transition (Story portal / Fighter VS / plain variant, chosen from the destination path), parents it to the autoload so it survives `ChangeSceneToPacked`, runs it at `ProcessMode.Always` so a paused tree cannot freeze it, and enforces a two-second minimum display time.
- Cross-scene selections live in `GameManager.CurrentSession` (`SessionData`): selected character, selected stage, active save slot, difficulty, and `MatchSettings`.
- Default match settings are Stock mode, 3 stocks, 480 seconds, items on/high, and hazards on/high.
- `StoryManager` defines target paths for levels 0–15 and **all sixteen scene resources now exist** (Package 5, 2026-08-08). It still validates a route before loading rather than changing to a broken scene. `tests/integration/CampaignRouteTests.cs` asserts that all sixteen routes resolve on disk, that the manifest's `StoryLevel` paths agree with `StoryManager.GetLevelScenePath`, and that a sequential advance 0→15 lands on a real scene at every step and caps at 15. Every level is a functionally complete flow with placeholder presentation.
- Levels 2–15 are built on `StoryLevelControllerBase` (`scripts/Environment/`): geometry builders, `RoomTransitionTrigger` + `StoryCameraConfiner` room graphs with resume-time camera re-confinement, three checkpoints per level (`{levelID}_checkpoint_{0,1,2}`), dust tally, boss wiring, extractor placement, a virtual post-boss/exit/completion tail, and pooled-object release on unload. **The Tutorial and Florence deliberately do not extend it** — they predate the convention and were not retrofitted, which is why their manifest rows are still `Prototype` while 2–15 are `Implemented`.
- Level 15 ends the campaign rather than returning to the hub: post-boss beat → Temporal Core insertion at the Prime Anchor → `CampaignCompletionSequence` (ending dialogue → credits → `SaveManager.MarkCampaignCompleted()` → MainMenu). The completion flag is written when the credits **begin**, so quitting mid-roll cannot lose a campaign the save has already advanced past. When a save `IsCompleted`, the hub's Temporal Portal shows a "timeline restored" state instead of reloading level 15.
- `TestArena` uses `FighterSimulationDriver`: Klotho state is authoritative and the two `PlayerController` nodes are collision-free presentation adapters. The local human/CPU match core, rules, results, rematch flow, and stage select are functional. **All ten catalog stages are authored production-contract scenes** (`scenes/fighter/FighterStage_*.tscn`, Package 6, 2026-08-08): each has its own `FighterStageGeometry` entry (fixed-point walls, ceiling, blast zone, spawn distance, two or three one-way platforms over a solid floor, hazard and orb anchors), its own `FighterStageController` scene with era-distinct placeholder presentation and a `ParallaxBackground`, its own `FighterCamera` midpoint/zoom wiring, its own pool config, its own `StageAudioSet`, and its own preview plate. Each stage carries one of ten era-specific deterministic hazard identities with real warning/active/recovery phases (`CooldownFrames` is the recovery length), per-type movement/targeting/dwell/idle behaviour, one-shot per-fighter hit masks where specified, and the block-absorbs-a-tick rule at one shield charge. `FighterStageConformance` (shared validator) pins every scene's markers and colliders against its fixed-point geometry through `pixel = (950 + x*62.5, 700 - y*62.5)`, and every stage ships a per-stage GdUnit suite. Production art, music, and VFX remain Package 8.
- Campaign scenes attach shared services through `StorySceneBootstrapper` (`scripts/Environment/`): a resource-driven `DialogueManager`, reusable `StoryHUD`, pause menu, and (for levels) the rewind manager and presentation overlay. Dialogue content lives in `DialogueSetData`/`DialogueSequenceData` resources under `resources/Dialogue/`.
- The Tutorial (fracture presentation, calibration, mobility gates, combat trial), Florence (gear-puzzle room gating, triggered waves, boss, results, autosave), and hub (Calibration Bay anchor, Holodeck CPU practice loop that returns to the hub, Sarah NPC, dust auto-deposit) flows are functionally complete with placeholder presentation. `StoryDifficultyTuning` scales Story enemy HP/damage at spawn without touching Fighter loadouts.
- Level *geometry, actors and hazards* are still built programmatically in the level controllers — valid prototyping state, not the intended final asset pipeline. **UI is no longer in that bucket**: as of Package 8 every production screen (main menu with its four-screen stack, Fighter character/stage/rules select, settings, both pause menus, both HUDs, dialogue box, resonance grid, level and match results, both loading variants, credits) is an authored, themed, focus-authored `.tscn`. Where a widget's *count* is data-driven (stock pips, shield charges, cooldown slots, resonance node buttons, character tiles' colour identity) it is still built in code inside the authored scene, deliberately — authoring a fixed number would cap the HUD at today's defaults.

## Autoloads and system ownership

`project.godot` currently registers these persistent autoloads:

- `EventBus`: typed C# events/payloads for non-adjacent system communication.
- `GameManager`: session data, defaults, and async scene transitions.
- `StoryManager`: campaign level, dust, rewind count, and hub/level flow.
- `PoolManager`: scene-pool registration, warm-up, spawn/release, and overflow policies.
- `InputManager`: action names, local controller assignment, and dedicated Roll capture (the deterministic Dash gesture conversion was removed with the universal dash, 2026-08-09).
- `SaveManager`: three story slots and global settings/statistics.
- `AudioManager`: AudioServer bus control and music/SFX entry points.
- `HapticFeedbackManager`: controller vibration settings and triggers.
- `CameraShake`: shared hit/impact feedback service.
- `LocalizationManager`: translation setup and lookup support.
- `ViewportEnforcer`: viewport/aspect enforcement hook.

Use the existing static `Instance` pattern for these services. Non-adjacent systems should communicate through `EventBus`; adjacent scene relationships should use exported references or explicit typed `GetNode<T>()` paths. Subscribe in `_Ready()` and unsubscribe in `_ExitTree()`. Avoid recursive `FindChild()` and repeated string-based scene-tree searches.

`NetworkManager` and `MatchmakingManager` are not current autoloads and are not wired into production flow.

## Gameplay architecture

### Character data and runtime controller

- Static identity and baseline tuning are Godot `Resource` objects (`CharacterData`) stored as `.tres` files.
- Story runtime behavior is owned by `PlayerController : CharacterBody2D`. Fighter runtime behavior in the Test Arena is owned by `FighterSimulation`; `PlayerController` is presentation-only there.
- The canonical state set is `Idle`, `Running`, `Dashing`, `Rolling`, `Skidding`, `Crouching`, `Airborne`, `Attacking`, `UsingSpecial`, `UsingUltimate`, `Blocking`, `Stunned`, `Dazed`, `LedgeHanging`, `Dead`, `Respawning`, and `UsingMovementAbility`.
- Universal movement uses a fourteen-frame grounded run ramp, a twelve-frame grounded stop/decel ramp (gameplay-feel batch 2026-08-10; `RunAccelerationFrames`/`RunDecelerationFrames`), a stateless fast-fall (Down held while airborne clamps vertical speed to `FastFallSpeed` 16 units/s downward and cancels Warp float, both modes, no snapshot state), and a 4-startup/12-travel/10-recovery evasive roll; the first eight roll-travel frames are invulnerable and roll travel disables the combatant pushbox. These timings live in `UniversalMovementRules` and must remain aligned between Story and Fighter simulation. **The universal dash was removed on 2026-08-09 by explicit user decision, superseding `design-godot.md`'s 12-frame `1.35x` dash spec** — the roll and each character's movement ability are the mobility tools. `CharacterState.Dashing`, `UniversalMovementPhase.Dash`, and the protocol-v2 Dash button bit remain reserved (never reuse them); enemy `ChargeDash` archetypes and character abilities that dash by name are unrelated and stay.
- Movement also includes direction-reversal skid, coyote time, jump buffering, short-hop behavior, air control, crouching, one-way platform drop-through, ledge hanging, and recovery. **Every character has a double jump as of 2026-08-10** (`MaxJumpCount` is 2 across the roster; run speeds −15% and jump forces −20% height in the same batch — the nine `.tres` values are law). The Fighter sim also ledge-grabs at authored platform ends (`FighterLedgeRules`, plan §2.11: capture falling or rising slowly into a 0.5-unit edge box, hang refills jumps, Jump climbs at 0.9× jump speed, Down releases with a 30-frame regrab lockout, 300-frame auto-release, hits knock the hang off); Story keeps its marker-based `LedgeGrabPoint` system, now also capturing while rising slowly.
- Story Mode may use native Godot `CharacterBody2D` physics. Local Test Arena Fighter Mode already uses Klotho fixed-point authority and must remain on that boundary; online work must not move authority back into `PhysicsServer2D`.

### Combat

- Hit detection is conceptually `Area2D` hitboxes against `Area2D` hurtboxes. Final activation timing should come from exact animation-frame callbacks, not broad body collisions.
- The basic combo has three hits using `0.8×`, `1.0×`, and `1.5×` `CharacterData.BasicAttackDamage` (the authored base damages were halved and Special1/Special2 `BaseDamage` doubled in the 2026-08-10 gameplay-feel batch; ultimates and movement abilities unchanged). Crouched and grounded-down attack inputs use the same three-hit string. **Two directional single strikes exist alongside the chain (2026-08-10):** Up held + attack is an upward launcher (grounded or airborne), and Down held + attack while airborne is a downward-hitting launcher (down-air); both use `BasicComboRules` frame data (7/8/18 and 6/10/16), 1.0× damage, 30-frame hitstun, mostly-vertical launch knockback, never chain, and reset the combo index. Selection is the shared pure helper `BasicComboRules.SelectAttackVariant`. The new `gameplay_up` action (W / stick-up / dpad-up) feeds the vertical axis; Jump no longer contributes to it, so Warp-style up reads follow the Up input.
- **Basic-combo timing and chain rules live in `FTT.Combat.BasicComboRules`** (2026-08-09 cross-mode parity pass, revised same day for attack-on-the-move): per-hit startup/active/recovery frames (grounded totals 27/30/45, aerial 25/28/40), the 30/40/24-frame hitstun table (hits one and two hold a non-blocking victim through the buffered chain's connect-to-connect gaps — but a grounded victim holding Block escapes hitstun into the stance as of 2026-08-10), the 1x/1.2x/**4.5x** `KnockbackMultipliers` (the finisher launches the victim beyond melee range — ≥2.5 units separation pinned across all nine kits), the 24-frame chain-hold/buffer window, the Story-enemy 24-frame stun floor for `combo_N` hits, and the block-regen interval. Story's `PlayerController` timelines and the Fighter sim's phase machine (`FighterBasicAttackRules` in `scripts/FighterSim/FighterSimulationSystems.cs`) both consume it — never author a second copy of these numbers. Unified behavior in both modes: **swings keep full input steering** (grounded run ramp and aerial drift alike) with facing following held movement mid-swing (2026-08-10, superseding the whole-string facing commit; hitbox placement still reads facing at active-start); **held movement never cancels or resets the chain** (movement-cancel let a moving attacker restart hit one faster than the authored pace); jump/roll/block cancel the recovery and chain-hold window and reset the chain; a special or the ultimate cancels a swing at any point; landing cancels an aerial string with no lag; being hit into hitstun cancels the string; whiffed swings chain only through the buffer/hold window; and knockback **replaces** velocity.
- Specials and ultimates use `AbilityData.BaseDamage`; multi-hit totals derive from per-hit damage and hit count.
- Knockback target: `baseKnockback / (1 + target.Weight)`, then scaled by the victim's missing HP after the hit — `×(1 + missingHPFraction)`, linear 1× at full HP to 2× at zero (`BasicComboRules.LowHealthKnockbackScale`; sim chokepoint `FighterDamageRules.ApplyFighterHit`, Story `DamageCalculator` overload; `BossController.ApplyKnockback` deliberately unscaled — recorded open inconsistency). There is no armor/defense stat that reduces HP damage.
- A special may cancel a basic attack when allowed by the FSM/cooldown rules. Block may cancel only during recovery frames.
- Blocking stops movement and is front-facing. Three basic hits exhaust the three shield charges; any special shatters the shield; ultimates bypass it. Guard break causes a one-second daze. Both modes enforce the grounded block stance (2026-08-09): no absorb while airborne, mid-swing, or mid-roll — and as of 2026-08-10 **holding Block while grounded in hitstun cancels the hitstun into the stance** (airborne victims and the guard-break daze cannot cancel); attack and ability inputs are ignored while the stance is up; and one charge regenerates per `BasicComboRules.BlockChargeRegenFrames` (180) while not blocking, in the sim as well as Story. The design's 2.0 s regen figure and 5 s shatter-lockout remain open questions (audit H-5).
- The Influence/Ultimate meter ranges from 0 to 100. Damage dealt adds 1 point per HP; damage taken adds 0.25 per HP. Using the ultimate resets it. Fighter stock loss retains 75% of the current meter.
- Fighter Mode is HP plus stock, not ring-out-only combat. A timer draw compares stocks, then HP percentage; a true tie is logged as a match but not a win or loss.

### Ability implementation

- Shared ability metadata belongs in `[GlobalClass] AbilityData : Resource`.
- Executable abilities derive from `BaseSpecial` and follow startup → active → recovery → cleanup phases.
- Character-specific classes live in `scripts/Characters/Abilities/` and use the `FTT.Characters.Abilities` namespace.
- Persistent constructs such as Tesla coils, Leonardo's turret, vine snares, serpent nests, projectiles, VFX, enemies, pickups, and damage numbers should use `PoolManager`/`IPoolable` rather than repeated instantiate/free churn during gameplay.
- Persistent objects must have stable owner/type/state data so Story rewind and Fighter rollback can snapshot them.
- The current `CharacterFactory` constructs placeholder character visuals and combat child nodes in code, but consumes canonical character/ability `.tres` tuning. Long-term presentation should move toward reusable authored scenes without reintroducing duplicate numbers.
- `PlaceholderProjectile`, `PlaceholderZone`, color rectangles, and code-generated labels are scaffolding. Do not mistake them for production art or final VFX.

### Status effects

The target design allows one active status at a time; the newest status completely replaces the previous one. Effects do not stack, and there is no general cleanse or post-effect immunity.

The enum, strategies, ability data, events, and deterministic runtime use the canonical `TimeDilation`, `Venom`, `StaticCharge`, `RadiantBurn`, and `Root` names. Both Story and Fighter adapters enforce newest-status replacement. Update both snapshot paths and tests when changing status semantics.

### Collision layers

Layers 1–11 are named Player, Enemy, PlayerHitbox, EnemyHitbox, PlayerHurtbox, EnemyHurtbox, Environment, OneWayPlatform, Trigger, PersistentObject, and Projectile. `CollisionLayers` centralizes constants and masks, and tests validate the matrix. Player/Enemy body masks deliberately remain physically separate; child `CombatantPushbox` Areas use those body layers for explicit soft horizontal jostling without making hurtboxes solid or allowing combatants to become floors. Ordinary enemies are roll-through, while large bosses can set `BlocksRollThrough`. Update project settings, constants, scene masks, pushboxes, and tests together.

## Story progression, rewind, and saves

- Story difficulty scales enemy HP/damage/spawn pressure/drop rates and Chronal Rewind behavior; it must not alter Fighter Mode balance.
- Rewind pools: Easy 5 with 100% HP restore and checkpoint refill; Normal 3 with 50% HP restore and +1 per new checkpoint; Hard 1 with 30% HP restore and no checkpoint refill during the level.
- Rewind state records at 60 Hz and searches backward for a safe grounded frame, retaining a last-known grounded fallback beyond the normal five-second/300-frame buffer. If none exists, use the physical checkpoint.
- Chronal Dust funds the selected character's Story-only Resonance Grid. Progress and unlocked node IDs belong to the story save slot. All nine baseline 3x3 grids are authored; the generic Story stat resolver and character-scoped modifier queries exist. `CharacterFactory` populates `PlayerController.StoryAbilityPerks` from the active save (Story-only; abilities gate bespoke behavior via `HasStoryPerk`). Einstein's three major perks are wired; the other eight characters' perks land with their kit passes (`docs/PACKAGE3_KIT_AUDIT.md`).
- There are three story slots plus global settings/statistics. Autosave occurs at checkpoints, level completion, and unlock events. The main menu supports localized slot summaries plus confirmed deletion of the exact primary/backup/temp/corrupt candidates for a slot.
- Save schema version 3 uses AES-256-CBC, encrypt-then-HMAC-SHA-256, distinct derived encryption/authentication keys, and a random per-install key stored at `user://saves/.savekey`. Writes are atomic and verified, backups can recover a bad primary, corrupt candidates are preserved, legacy Base64/plain JSON is migrated, completed puzzle IDs persist per slot, and newer schemas are rejected without rewriting them. Never replace the per-install strategy with a hardcoded source secret.

## Fighter networking and determinism

`scripts/FighterSim/` implements a Klotho fixed-point (`FP64`/`FPVector2`) 1v1 foundation with quantized inputs, stable state IDs, full snapshots, deterministic hashes, a 120-tick history, prediction, corrected-input rollback, and resimulation. `FighterLoadoutFactory` accepts normalized base resources only, preserving Story/Fighter isolation. The Test Arena renders synchronized results without feeding Godot state back into gameplay.

The deterministic systems cover accelerated ground/air movement, universal roll phases (dash removed 2026-08-09), fixed-point fighter jostling, jump counts, solid side/top bounds, bottom-zone stocks, generic basics/specials/ultimates, block, meter, status, Stock/Time/Hybrid resolution, projectiles, movement abilities (including input-directional Warp teleports with a reduced-gravity float window), deploy-limited persistent constructs, Area-execution zones (`FighterZoneComponent`/`FighterZoneSystem`: impulse-free periodic damage/status pulses that bypass shields and never zero velocity, plus owner-overlap speed bonuses like Einstein's Relativity Rift), stage hazards, and Chronal Orbs. `FighterStageGeometry` supplies per-stage fixed-point bounds, one-way platforms (with drop-through and edge-walk-off rules), spawn distance, and authored hazard/orb anchors; stages without authored geometry fall back to the legacy flat arena. Stages with platforms have a solid base floor. Character-specific production behavior and rollback performance/platform gates remain incomplete. Klotho v0.6.1 is experimental and this is not production online netcode.

`scripts/Networking/` now defines a versioned fixed-size input/hash protocol (currently protocol v2, including Roll/Dash button bits), acknowledgements, confirmed-frame hash exchange, direct-IP UDP LAN transport, deterministic in-memory test transport, remote prediction/correction, bounded rollback/resimulation, desync events, rollback-budget diagnostics, and cryptographically generated room codes. It does not yet have LAN discovery, handshake/rules negotiation, full-state resync, matchmaking UI, Steam Networking Sockets/relay, public queue, or production failure/forfeit flows.

Initial online/local Fighter Mode is 1v1. Even if code contains generalized player-count fields, do not build four-player behavior in this phase.

## UI, localization, audio, and accessibility

- UI is authored for a 1920×1080 reference canvas with Godot `Control` anchors and layout containers.
- **One shared theme.** `resources/UI/ftt_theme.tres` is the single `Theme`; adopt it by setting `Theme` on a screen's root `Control` and Godot propagates. `scripts/UI/UIPalette.cs` holds the matching C# colour constants for `ColorRect` fills and runtime tints that a Theme cannot express, and `UIThemeTests` fails if the two drift. The theme deliberately carries no font resource (`assets/fonts/` is empty); dropping in a production face later is a one-line `default_font` addition.
- **Author focus, do not rely on Godot's geometric fallback.** `FocusChainBuilder.Apply(container)` writes `focus_neighbor_*` links and takes initial focus; rebuild the chain whenever a surface shows or hides options. `Collect` skips hidden subtrees and `focus_skip` group members, and splices a `SpinBox`'s internal `LineEdit` in at the spin box's own position (internal children are invisible to `GetChild`, so a spin box is otherwise unreachable by keyboard and controller).
- **`PauseMenuBase` owns `SceneTree.Paused`** for both `PauseMenu` (Story) and `LocalFighterPause`; subclasses may layer presentation but cannot skip the tree write, and an overridden `_ExitTree` must call `base._ExitTree()`. `SettingsMenu` never writes the pause — closing it returns control to whoever opened it.
- **Loading is a themed scene, not a code-built overlay.** `GameManager.LoadScene` picks a Story portal or Fighter VS treatment from the destination path and keeps the 2 s minimum display time.
- Use `Tr("translation_key")` / `TranslationServer.Translate(...)` or the localization manager for all visible copy. Add English entries to `localization/en.csv`. Do not add localized JSON payloads or language selectors until localization production is scheduled.
- **In an authored `.tscn`, store the raw key as the control's `text` and let Godot's automatic control translation resolve it** — that is what lets a language change follow without rebuilding the surface, and scene tests assert the raw key rather than the English string. `SceneVisibleTextTests` rejects any visible `text` that is neither a real translation key nor an empty/glyph-only value; `ScriptTranslationKeyTests` sweeps every `Tr("...")` and `TranslationServer.Translate("...")` literal in `scripts/`; `UnusedTranslationKeyTests` reports keys nothing references and fails on a new one.
- `project.godot` registers `res://localization/en.en.translation` with English fallback. Keep that resource registration intact: Godot `Node.Tr()` bypasses the custom `LocalizationManager` and otherwise displays raw translation keys as placeholder text.
- Dialogue uses a 30-characters-per-second typewriter reveal with punctuation holds (0.26 s after `. ! ?`, 0.12 s after `, ; :`, a run of marks holding once), a glass panel treatment, emotion-driven portrait framing, and a chirp every third non-whitespace character pitched per the locked character. Confirm completes the active line silently, then advances on the next confirm. Full dialogue-sequence skipping is not supported.
- **Audio buses are authored** in `resources/Audio/default_bus_layout.tres` (Master → Music, SFX → {Combat, Movement, Environmental}, UI), registered under `audio/buses/default_bus_layout`. `AudioManager`'s `StemDirector` plays a `StageAudioSet`'s three stems synchronized and **additively** — ambient always audible, combat layering on, climax on top — with authored crossfades; `AudioSnapshotMixer` layers pause/low-health/ultimate/rewind ducking and low-pass over that. All 27 audio sets (17 Story + 10 Fighter stages) are authored on placeholder stems. **The entire placeholder audio kit is digital silence as of 2026-08-10 (user directive: the placeholder tones were annoying)**: the three stems, the five generated .ogg cues (the generator's documented RENDER_SILENT flag keeps durations byte-identical), and the six one-shot SFX .tres payloads — which also silences the dialogue chirp, footsteps, UI blips, and hit/hazard/pickup cues. Durations, loop metadata, paths, and all call sites are untouched, so every audio contract test still holds and Package 10's real assets drop in with no code changes — do not "fix" the silence by re-adding tones (resources/Audio/README.md carries the full record). Saved volumes apply at boot.
- Settings include audio buses, resolution/window mode/VSync, complete InputMap rebinding with conflict explanation and reset-to-default, damage-number visibility, HUD opacity, screen-shake scaling, and haptics. All of it persists in global save data (schema v4 for the global payload).
- Controller haptics and screen shake must respect their global accessibility intensity/enable settings. `HudOpacity` is polled live, not read once at construction.

## Coding and content conventions

- Match folder namespaces: `FTT.Core`, `FTT.Characters`, `FTT.Characters.Abilities`, `FTT.Combat`, `FTT.Enemies`, `FTT.Environment`, `FTT.UI`, `FTT.Networking`, and `FTT.FighterSim`.
- Godot C# node/resource classes are `partial`; reusable inspector data classes should use `[GlobalClass]` and `[Export]` fields/groups.
- Use `res://` paths for Godot resources. Prefer exported `PackedScene`, `Resource`, and typed node references over scattered magic paths.
- Keep static tuning in Resources and runtime mutable state in controllers/snapshots. Avoid creating a second canonical value in a factory or UI script.
- Poll named InputMap actions through `InputManager.Actions`. Preserve device/player separation for local 1v1; direct global input polling can make both fighters react to one device.
- Gameplay state changes belong in `_PhysicsProcess()` at 60 Hz. `_Process()` is appropriate for presentation/loading/UI, not authoritative combat simulation.
- Use `EventBus` for cross-system events, but keep payloads sufficient for consumers and avoid hidden global coupling.
- Pool frequently spawned or destroyed gameplay objects. Reset every mutable field in `OnSpawn()`/`OnDespawn()`.
- Dispose engine-returned Godot collection wrappers (`GetNodesInGroup`, `GetChildren`, `GetOverlappingBodies`/`Areas`) deterministically at recurring gameplay call sites: bind the result, then `using var lifetime = result.AsDisposable();` (`FTT.Core.GodotCollectionExtensions`). Wrappers left to the GC land on the finalizer queue, and a collection finalizer that runs during engine teardown crashes the process (`0xC0000005` in `godotsharp_array_destroy`); `GameManager._ExitTree` drains the queue at quit as the backstop, but deterministic disposal is the first line of defense and also avoids gameplay-time GC pressure.
- **Never call `Dispose()` on a Godot `Resource`** (or any `RefCounted`), in production or test code. Reference counting owns their lifetime. Disposing one that another Godot object still references — or that a parent resource will release — double-disposes its C# script instance and trips `CRASH_COND(gchandle.is_released())` in `mono_object_disposed_baseref`, which kills the process with `0xC000001D` at some unrelated later point. `Free()` the *node* and leave its resources alone.
- **Load authored `.tres` data resources through `FTT.Core.AuthoredResources.Load<T>()`, not `ResourceLoader.Load`/`GD.Load`.** `CharacterData`, `AbilityData`, `EnemyData`, `BossData`, `EnemyAbilityData`, `ResonanceGridData`, `DialogueSetData`, `ScenePoolConfig`, `StoryDropTable` and friends are immutable tuning data; the cache pins each one for the process lifetime. Loading one, reading it, and dropping the reference destroys the whole scripted graph — including every sub-resource behind an `Array[ExtResource(script)]` export — and rebuilds it on the next call, and that churn races the .NET finalizer thread into the same crash. Scenes, textures, audio, and anything pooled or streamed must *not* go through the cache; they are meant to be released.
- **Whoever sets `SceneTree.Paused` hands it back, including on teardown.** Release it in `_ExitTree` as well as on the normal path (`DialogueManager`, `PauseMenu`), and restore it in a test's `finally`. A leaked pause freezes the next scene in game, and under GdUnit4 it stops the runner's transport node and hangs the whole test session.
- Keep Story-only progression modifiers out of shared Fighter stats and ability resources.
- Preserve historical framing and the selected character's ability identity when adding mechanics; mechanics should not become generic solely for implementation convenience.
- Update translation keys, save schemas/migrations, rollback snapshots, pools, and tests whenever a changed data field affects them.
- Preserve unrelated user changes in this working tree. Do not clean, reset, or rewrite generated/user-modified files outside the task.

- **Never author an empty Script-typed array in a `.tres` or `.tscn`.** `Prop = Array[ExtResource("N")]([])`, where resource `N` is a `.cs` script, corrupts the Godot 4.7.1 .NET heap when the resource is marshalled to its C# array export. The process then dies at an unrelated site — a silent GdUnit child death (exit `-1073741819` / `-1073741795`), a hang, or `ResourceLoader.Load` returning null for an unrelated resource — so the crash never points at the cause. To express "no entries", omit the property and let the C# field default apply. Non-empty Script-typed arrays are fine, and so are empty arrays of builtin types (`Array[float]([])`, `Array[int]([])`). `tests/ContentValidation/ScriptTypedEmptyArrayTests.cs` scans the content directories and fails with the offending file and line. This cost a full debugging cycle in Package 4 B6; see that plan's Deviations section.
