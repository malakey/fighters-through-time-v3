# Implementation audit — 2026-08-08

A deep review of the current implementation against `design-godot.md`, the accepted ADRs, and the package plans, performed after the Package 8 close (baseline: 1293/1293 tests green). The explicit goal was to find what the project's own tracking does **not** already record. Everything already documented — `IMPLEMENTATION_PLAN.md` package status and deferrals, `AGENTS.md` known gaps, both `IMPLEMENTATION_STATUS` files, the per-package deviation logs (`PACKAGE3_KIT_AUDIT.md`, `PACKAGE4_ROSTER_PLAN.md` §8, `PACKAGE5_CAMPAIGN_PLAN.md` §9, `PACKAGE6_FIGHTER_PLAN.md` §9, `PACKAGE8_PRESENTATION_PLAN.md` §9), and `DUST_ECONOMY.md` — was treated as known and excluded. Placeholder assets, Package 7 (online, deferred by user decision), Package 9 (QA/perf), and Package 10 (asset replacement) scope are likewise excluded.

**Method.** Nine parallel domain reviews (story campaign/hub/grid; character kits/stats/talents; shared combat & movement in both modes; enemy/boss roster & AI; save security + core autoloads; networking + determinism boundary; Fighter stages/hazards/orbs/match flow/CPU; UI/audio/settings/localization; cross-cutting lifecycle/isolation/test-integrity sweeps). Every finding cites `file:line` evidence read from the implementing code, and each was checked against the known-gap documents above before inclusion. Findings marked **✅ re-verified** were additionally confirmed by direct code reads during synthesis (the Critical, both High-impact economy/save items, and the headline Fighter items among them).

**Severity calibration.** Severities are honest to context: save-tamper findings are judged against ADR 0004's *own* stated threat model (local, per-install key), network findings against a LAN/direct-IP foundation whose production hardening is deferred with Package 7.

## Executive summary

The foundations this repository is most worried about are in genuinely good shape: the deterministic simulation boundary is clean (no float math, no unseeded randomness, no Godot state feeding the sim; snapshot completeness spot-diffed), the save envelope's cryptographic core is correctly built (encrypt-then-MAC verified before any parse, constant-time compares, fresh IVs, CSPRNG keys), EventBus subscribe/unsubscribe is balanced repo-wide (88/88), `SceneTree.Paused` ownership is disciplined, Story→Fighter isolation holds, and there are zero TODO/FIXME markers in 234 scripts. The conventions in `AGENTS.md` are actually followed at roughly 99% of call sites.

The audit nonetheless found **1 Critical, 10 High, and ~30 Medium** previously-untracked issues. They cluster into six themes:

1. **A pooled-signal lifecycle bug family silently guts Story combat** (Critical). `Hitbox` connects its only hit-delivery signal in `_Ready` (once per node lifetime) and disconnects in `_ExitTree` (fires on every pool reparent). Warmed enemies and projectiles can never deal damage; fresh instances work for exactly one pool cycle. The four damageable constructs are indestructible by the same flaw. The correct pooled `_EnterTree`-rebind pattern exists in the repo (Package 8's `GlowPresentationController`) but was never retrofitted.
2. **"Universal" mechanics have drifted apart between Story and Fighter.** Block (regeneration and stance rules), gravity/jump physics, combo-chain semantics, hitstun sourcing, drop-through input, pushbox geometry, and a set of designed-universal movement mechanics each follow different rules per mode — against the design's central cross-mode-coherence pillar. Most divergences are recorded nowhere.
3. **The dust economy as played diverges from the locked model.** Every mob kill pays twice, the 50% quit-to-menu penalty that `DUST_ECONOMY.md` models does not exist in code, the results overlay under-reports, and five authored elites can never appear in a playthrough.
4. **Several designed behaviors are wired but dead.** Pause/low-health/ultimate audio snapshots are never triggered; the Settings screen has no focus authoring (a controller cannot operate it at all); the Fighter match seed is a hardcoded constant so every match runs the identical orb/hazard script; the bottom blast zone — a stated product pillar — is unreachable on all ten production stages.
5. **Save security has one real hole beyond its accepted model**: a permanent unauthenticated legacy-format fallback that bypasses the entire HMAC envelope, plus a backup-rotation defect and a silent-brick failure mode on a corrupt key file.
6. **The root `IMPLEMENTATION_STATUS.md` overclaims at least ten rows** (marked Implemented where the behavior does not exist), which matters in a repo whose agent workflow leans on documentation accuracy.

## 1. Critical

### C-1. Pooled `Hitbox` hit detection permanently dies after one pool cycle ✅ re-verified

**Category: BUG.** `scripts/Combat/Hitbox.cs:52-64` — `_Ready()` runs `AreaEntered += OnAreaEntered` and `_ExitTree()` disconnects it. In Godot, `_Ready` fires once per node lifetime, but `PoolManager` reparents on every cycle (`scripts/Core/PoolManager.cs:139` `RemoveChild` on spawn, `:223-228` `RemoveChild`→`AddChild(InactiveContainer)` on release), and `_ExitTree` fires on each `RemoveChild`, propagating to all descendants. `OnAreaEntered` (`Hitbox.cs:92-100`) is the **only** delivery path — `Activate()` only sets `Monitoring`, and `HitboxSystem.cs` is just the payload struct. A repo-wide grep confirms `Hitbox.cs:55` is the only connect site.

Consequences, verified against the pool code:

- **Warm-up instances are dead on arrival.** `RegisterPool` adds warmed nodes to the in-tree `InactiveContainer` (`PoolManager.cs:94-101`), so `_Ready` runs and connects; their *first* spawn's `RemoveChild` then fires `_ExitTree` and disconnects forever (`_Ready` never re-fires on reparent).
- **Fresh instances work exactly once.** Created on demand, they connect on first `AddChild`, then die on first release.

Affected: `PlaceholderProjectile` (the shared pooled projectile behind Joan's Righteous Smite, Einstein's E=mc², Mozart's Requiem/Fortissimo, Shakespeare's Yorick — pool registered with warm-up 1 at `BaseSpecial.cs:193`), `EnemyProjectile` (level 2 alone warms 18 — all inert), and every pooled enemy's melee/charge/pulse attacks, which `EnemyAbilityExecutor.ActivateHitbox` (`EnemyAbilityExecutor.cs:236-261`) delivers exclusively through the scene `Hitbox`. Level pool configs warm `standard_enemy` 10 / `elite_enemy` 3, so **campaign enemies deal no contact damage from their first spawn**. Fighter Mode is unaffected (the deterministic sim does not use Area2D hitboxes), and the player's own melee hitboxes survive (the player node is never pool-reparented).

Why nothing caught it: kit/enemy tests never assert a hit on a second-cycle or warmed instance, headless smoke runs don't fight, and the documented "no human playthrough yet" gap means no one has felt it. The repo already knows the correct pattern — `EnemyController` rebinds its hurtbox in `OnSpawn()` with an `_eventsBound` guard (`EnemyController.cs:150-165, 761`) and `GlowPresentationController.cs:87` binds in `_EnterTree` (Package 8 codified this as "the pooled `_EnterTree` signal-binding rule") — it was never applied to `Hitbox`.

**Fix shape:** bind in `_EnterTree` behind the existing `_areaEnteredConnected` guard (or simply never disconnect — Godot signal connections survive reparenting; the `_ExitTree` disconnect is the self-inflicted wound). Add a regression test that spawns→releases→respawns a pooled projectile and asserts a hit lands on cycle two, and one asserting a warmed enemy's melee lands on cycle one.

## 2. High

### H-1. Every enemy kill's Chronal Dust is awarded twice ✅ re-verified

**Category: BUG (economy).** `scripts/Environment/StoryLevelControllerBase.cs:266-269` — `OnEnemyKilled` both tallies and re-raises the award (`RaiseChronalDustCollected(payload.ChronalDustDrop)`), while `scripts/Environment/StoryDropSystem.cs:29-32` (present in every campaign scene) independently spawns a `ChronalDustPickup` carrying the same amount, which raises the same event again on magnetized collection (`ChronalDustPickup.cs:70-71`; 150 px magnet radius means near-always in melee). `StoryManager.cs:297-299` adds both into the wallet. `Level01Controller.cs:651-654` has the identical re-raise, so levels 1–15 double-pay; the Tutorial's handler doesn't re-raise, so it single-pays — the inconsistency is itself the tell. The pickup's own comment (`ChronalDustPickup.cs:72-75`) acknowledges the event fires twice per kill but treats it only as an audio-cue dedup concern.

Impact: mob income up to 2× the locked `DUST_ECONOMY.md` model (~+350–400 dust on a Normal campaign), collapsing the documented pacing milestones (first major perk near the Act I finale, full-grid crossing), and the inflated wallet persists via checkpoint autosave. Content tests miss it because fixtures raise `OnEnemyKilled` without stepping pickup physics. Note the interaction with C-1: with warmed enemies unable to hurt the player, an inflated economy compounds into a much easier campaign than tuned.

**Fix shape:** decide the single awarding site (the physical pickup is the designed one — §3's pickup-tier rule), demote the controller handler to tally-only (`TallyDust`), and pin with a test that steps a kill through pickup collection and asserts the wallet moved exactly once.

### H-2. Save system: permanent unauthenticated legacy fallback bypasses the HMAC envelope

**Category: SECURITY.** `scripts/Core/SaveManager.cs:348-354` (story) and `:390-396` (global) — when envelope decode fails, `TryLoadLegacyStory` (`:568-579`) accepts **Base64-encoded plain JSON** and `TryLoadLegacyGlobal` (`:581-590`) accepts **raw plain JSON**, then re-saves the payload under the real key ("migrated" notice). ADR 0004 frames legacy migration as a **one-time development measure** to resolve "before external builds," and names integrity/accidental-edit resistance as primary goals. As implemented, writing plain JSON into `global.sav` (or Base64 JSON into a slot file, deleting `.bak`) loads with zero authentication and gets laundered into a validly-signed envelope — a strictly simpler attack than the ADR's accepted read-the-key model, and a hand-edited file is silently accepted instead of flagged as tampered.

Compounding it: **restored input bindings are applied to any `InputMap` action** (`scripts/Core/InputBindings.cs:258-276` gates only on `InputMap.HasAction`; the `RemappableActions` filter exists only on the legitimate write path), so a forged/legacy-migrated global payload can rebind `ui_accept` or the deliberately read-only `gameplay_ultimate` chord — `Normalize()` sanitizes numeric fields but not action names or event counts.

The rest of the envelope is sound (see §7): MAC-before-parse, `CryptographicOperations.FixedTimeEquals`, fresh per-write IVs, distinct derived keys, atomic write+verify, future-schema rejection.

**Fix shape:** gate the legacy paths behind a compile-time/dev flag (or delete them — no external build has shipped, so there are no real legacy saves in the field), surface "unrecognized format" as the tamper notice instead; filter binding restore through `RemappableActions` and cap event counts.

### H-3. All four damageable constructs are indestructible (C-1's sibling)

**Category: BUG.** `TeslaCoilNode.cs:46-53`, `SerpentNestNode.cs:38-45`, `LeonardoTurretNode.cs:38-45`, `VineSnareNode.cs:39-45` — each subscribes `_hurtbox.OnHit` in `_Ready`, unsubscribes in `_ExitTree`, and has an empty `OnSpawn()`. `Hurtbox.TakeHit` returns 0 when `OnHit` has no subscribers (`Hurtbox.cs:21`). Constructs spawn through `PoolManager.Spawn(PackedScene…)`, which auto-registers with warm-up 1 (`PoolManager.cs:121`), so the very first coil/nest/turret/snare of a session is a warmed instance whose subscription was severed on spawn — enemy attacks against it deal nothing; only lifetime expiry removes it. `design-godot.md:1042-1046` specifies the 25/20/15 HP destructibility as the counterplay, and `PACKAGE3_KIT_AUDIT.md` claims "damageable" for these slots. Same fix pattern as C-1 (rebind on `_EnterTree`/`OnSpawn`).

### H-4. Story abilities cannot be interrupted, and ability cleanup truncates an active stun

**Category: BUG / REWORK.** `BaseSpecial.cs:130-146` advances startup→active→recovery whenever `IsExecuting`, independent of the owner's FSM; `PlayerController.ApplyStun` (`PlayerController.cs:1115-1119`) transitions to `Stunned` without cancelling the executing ability, and nothing calls a cancel path from hit/death handling. So (a) multi-hit specials/ultimates keep dealing damage and steering the caster while stunned — `JoanGrandCrusade._PhysicsProcess` (`JoanAbilities.cs:303-320`) force-sets charge velocity every tick regardless of state; `EinsteinUltimate.OnRecovery` (`EinsteinUltimate.cs:80`) fires all remaining singularity hits after an interrupting hit; and (b) `BaseSpecial.OnCleanup` (`BaseSpecial.cs:106-113`) unconditionally transitions to Idle/Airborne (`TransitionTo` guards only `Dead`, `PlayerController.cs:1061`), so a stun inflicted mid-ability is cut short when the phase timer expires. The design treats hit-while-attacking→Stunned as canonical (§14, `design-godot.md:3310`) and hyper-armor as the *exception* (Joan `:1901`, Lincoln `:2193`) — meaningless if every special is inherently unstoppable. Fighter-side hitstun is handled correctly by the sim; this is Story-only.

**Fix shape:** an `Interrupt()` on `BaseSpecial` invoked from `ApplyStun`/death (skipped under hyper-armor), and make `OnCleanup` respect a non-Idle current state.

### H-5. Block-charge regeneration: design 2.0 s / Story 3.0 s / Fighter never — and no shatter lockout anywhere

**Category: REWORK (cross-mode).** `scripts/Combat/BlockSystem.cs:35` hardcodes `RegenInterval = 3.0f` (design `:1012-1013`: one charge per 2.0 s). The Fighter sim has **no code path that regenerates `BlockCharges`** — set at spawn (`FighterSimulationSystems.cs:77`), decremented on block (`FighterEntitySystems.cs:97`), reset only by stock loss (`:949`). The designed 5-second post-shatter lockout exists in neither mode. Net effect: in Fighter, three blocked jabs permanently disable a core defensive mechanic until you lose a stock; the same resource follows three different rules across design/Story/Fighter. Root `IMPLEMENTATION_STATUS.md:188-189` claims both the 2.0 s regen and the 5 s lockout are Implemented — neither is.

### H-6. Fighter block is a stateless held-button absorb

**Category: REWORK (cross-mode).** The sim's only consumer of the block button is `FighterEntitySystems.cs:84-86` (`targetBlocking = carriesImpulse && UniversalMovementState == None && (HeldButtons & BlockButton) != 0`) — no grounded requirement, no hitstun/daze exclusion; `FighterMovementSystem` never reads the button (movement unaffected) and `FighterCombatSystem.BuildIntent` doesn't either (you can attack while "blocking"). Story implements the designed stance (`PlayerController.cs:954-981`: grounded-only, decelerates to zero, attack inputs ignored, unreachable from Stunned). Design `:1004`: "Movement speed is locked to zero while holding the block button." In Fighter a player can hold block permanently while approaching, jumping, and attacking for free frontal absorption, and can block follow-ups mid-hitstun — a fundamental competitive-rules divergence in the mode that is supposed to be the competitive one.

### H-7. Gravity/jump physics: three-way divergence; Fighter drops short-hop and weight coupling

**Category: REWORK (cross-mode).** Story (`PlayerController.cs:178-182`): `BaseGravity = 18` (design 30), `FallGravityMultiplier = 1.8` (design 2.5), `ShortHopGravityMultiplier = 2.5` (design 3.5), terminal velocity 10 u/s (design 20); the weight formula (`:1315`) matches the design's shape on the wrong base. Fighter (`FighterSimulationSystems.cs:209`): flat `-30` — no weight factor, no fall multiplier, **no short-hop** (`ReleasedButtons` never consulted for jump; fixed-height jumps at `:499-513`), no terminal velocity. Jump impulse scale also differs (Story ×0.9 via `MaxJumpForce * 54` px/s at `:1410`; Fighter ×1.0 in `FighterLoadoutFactory.cs:42`). The same character rises and falls measurably differently between modes; heavier characters fall faster only in Story; short hops exist only in Story. Design refs `:681-684, 697-702, 1016-1019`.

Related Medium-tier members of the same theme are grouped under M-16…M-22 below (combo chain, hitstun sourcing, cancel windows, drop-through input, missing universal movement set, pushbox geometry, cooldown start timing).

### H-8. Mirror Paradox is exempt from the Chronal Rewind world freeze

**Category: BUG.** `ChronalRewindManager.FreezeWorldForRewind()` (`ChronalRewindManager.cs:153-172`) freezes groups `"Enemies"` and `"persistent_construct"`. Regular mobs/bosses are covered via their scene-root groups — but the Level 13 clone joins only `"Players"` + `"MirrorParadox"` (`MirrorParadoxController.cs:168-169`), and although both mirror controllers implement `IStoryRewindSimulation.SetStoryRewindFrozen`, **no runtime code ever calls it** (`Level13Controller.BuildMirrorEncounter`, line 466, wires no group/freeze). During a rewind the player is fully suspended while the Hard-CPU clone keeps simulating — repositioning onto the player's landing point, spending cooldowns, spawning attacks. Its projectiles also survive `ClearEnemyProjectiles()` (`PlaceholderProjectile.cs:64` puts only `ownerIndex < 0` shots in the `enemy_projectile` group; the clone's index is 1). `MirrorParadoxTests.cs:378` calls `SetStoryRewindFrozen(true)` directly — the mechanism is tested, the wiring is not. Every rewind in the campaign's signature boss fight visibly breaks the freeze contract.

### H-9. Pause / LowHealth / Ultimate audio snapshots are never applied

**Category: BUG (dead designed behavior).** `AudioSnapshotMixer.cs:84-87` defines all four snapshot tables; repo-wide, the only production `ApplySnapshot` caller is `RewindPresentationOverlay.cs:139` (Rewind). `PauseMenuBase.SetPaused` writes only `SceneTree.Paused`; nothing polls HP; `OnUltimateActivation` feeds only haptics. Design `:2812-2819` specifies GamePaused low-pass + UI boost, LowHealth heartbeat/muffle below 20% HP, UltimateCinematic −12 dB duck. The mixer machinery passes its unit tests while three of its four designed triggers are unwired. Root `IMPLEMENTATION_STATUS.md` §12 affirmatively claims "pause and low-health drive them."

### H-10. Settings screen has no focus authoring — controller/keyboard cannot operate it

**Category: BUG (accessibility/controls).** `scenes/ui/Settings.tscn` contains no `focus_neighbor` properties; `SettingsMenu.cs` has zero `FocusChainBuilder` references and `Show()` (`:416-420`) never grabs focus. Its openers keep their own chains live underneath: `PauseMenu.cs:159-165`, `LocalFighterPause.cs:196-202`, `MainMenu.cs:216-223` (MainMenu restores focus on `Closed` — proving the intended pattern). A controller/keyboard player can never reach any control inside Settings, and navigation input keeps driving the surface beneath the overlay (e.g. Enter can activate a pause-menu item under an open Settings screen). This contradicts Package 8's exit criterion ("controller-navigable ... on every screen") and is invisible to the scene contract tests, which assert nodes rather than focus.

### H-11. The bottom blast zone is unreachable on all ten production stages ✅ re-verified

**Category: DIVERGENCE (design conflict to surface).** The Package 6 fix correctly reordered the blast-zone check before the ground snap, but `FighterSimulationSystems.cs:311-319` then clamps `Position.y` to 0 whenever `groundIsSolid = _geometry.Platforms.Length > 0` — true for **every** authored stage. `FighterStageGeometry` has no floor-extent concept; x is clamped to the walls (`:286`), knockback y is always upward, drop-through is refused on the base floor, and warp clamps y ≥ 0 (`FighterEntitySystems.cs:687`). So the "falling off the bottom costs a stock" rule — a non-negotiable pillar in both `design-godot.md:22` and `AGENTS.md` — can only ever fire on the legacy no-platform TestArena geometry, and Paris's designed "two drawbridge walkways suspended over a central lower pit" (`:3113`) was flattened onto a sealed floor (`FighterStageGeometry.Paris`, `:154`). The "solid base floor" geometry decision is documented; its consequence — the pillar being inert across the production catalog, and the tested bottom-fall end condition being unreachable in real play — is recorded nowhere, and root `IMPLEMENTATION_STATUS.md` §22 claims bottom-fall stock loss is real. **This needs a design decision**, not just a code fix: either author at least some stages with open floor segments (Paris is the obvious candidate), or amend the pillar and retire the end condition.

### Fighter Mode

- **M-7. Every production match runs the identical RNG schedule ✅ re-verified.** `FighterSimulationDriver.Initialize` (`FighterSimulationDriver.cs:102-108`) never passes the `seed` parameter, so every match uses the default `2026` (`FighterSimulation.cs:30/42`). All orb types/anchors and hazard anchor/damage draws replay identically on a given stage — a rematch is literally the previous match's script. (The CPU stream is correctly derived from "the match seed" at `:114` — but the match seed never varies.) Design `:3131/3134` implies a per-match synchronized seed. One-line fix at the driver plus plumb the chosen seed into the (already session-scoped) match setup — and note the future Package 7 handshake must agree on it.
- **M-8. The CPU has no projectile awareness at any difficulty.** `CpuDecisionObservation` (`CpuDecisionObservation.cs:31-98`) carries no projectile fields; defense triggers only on `TargetPressedButtons` within 2 units (`FighterCpuController.cs:416-424`). Design `:3161/3175/3186` specifies Easy rarely / Medium sometimes blocking projectiles and Hard blinking through them. All zoner matchups (Einstein/Tesla/Mozart) meet a CPU that never reacts to anything in flight.

## 5. Security assessment

Scope: the save system (judged against ADR 0004's own threat model — tamper-resistance with a local per-install key; a local attacker who can read the key is accepted), the networking foundation (judged as a LAN/direct-IP foundation), and input-surface hardening. **No remote-exploitation surface exists in the shipping single-player/local paths today**; the findings below are about the project's own stated guarantees.

**What is sound** (verified in code): HMAC-SHA-256 verified over the full envelope **before** any header parse or decryption (`SaveEnvelope.cs:101-107`); constant-time comparisons (`CryptographicOperations.FixedTimeEquals`, also for the magic); encrypt-then-MAC with the MAC covering header+IV+ciphertext (padding-oracle closed); fresh CSPRNG IV per write; 32-byte CSPRNG master key with atomic creation; distinct enc/auth keys via domain-separated SHA-256 (sound at full entropy); atomic temp-write → flush → re-read-verify → `File.Move` replace; future-schema rejection without rewrite; Newtonsoft with default settings — **no `TypeNameHandling` anywhere**; numeric fields clamped in `Normalize()`; slot paths built from a validated 0-2 int, no user-influenced path strings; room codes from `RandomNumberGenerator` over a bias-free 32-char alphabet.

**The gaps, in priority order:**

1. **H-2 (High): the legacy fallback is a standing authentication bypass.** Plain JSON (global) / Base64 JSON (slots) loads unauthenticated and is re-signed. The ADR calls for this to be resolved before external builds; nothing gates it. Close it before any build leaves the machine.
2. **Input-binding restore trusts arbitrary action names** (part of H-2's blast radius): filter through `RemappableActions` on the *read* path and cap event counts, so a tampered global payload cannot rebind `ui_*` or the read-only chord.
3. **M-21: backup rotation can destroy the last-known-good backup** right after a recovery — an integrity-availability defect the ADR claims the opposite of.
4. **M-22: corrupt `.savekey` silently bricks saves** with no UI notice — the one artifact whose failure path violates the ADR's recoverable-error requirement.
5. **M-33 / Lows: the UDP receive path** should catch `SocketError.MessageSize` (and reject `count != 47` on all platforms — POSIX truncation currently smuggles a prefix through), bound `_remoteInputs` to a sane future window, and treat first-sender peer-lock as temporary until the Package 7 handshake adds endpoint authentication. Room-code entropy is fine.
6. **Envelope scope notes** (accepted-model boundaries, not defects): no slot-identity binding (cross-slot file copy authenticates), no freshness (old signed saves replay — effectively a user backup feature offline).

## 8. Recommended disposition order

**Batch 1 — mechanical fixes, high value, low risk (all have obvious single-site fixes):**

**Batch 2 — design decisions required before code (each changes tuned behavior):**

**Testing note.** The audit's most important meta-finding: the suite's blind spot is *second-cycle pooled behavior* and *cross-mode rule equivalence*. Two cheap permanent additions would have caught the worst of this report: a pooled-combat regression suite (spawn→release→respawn → assert a hit lands; warmed instance → assert first hit lands) and a shared-rule parity suite that runs the same scenario table through both the Story rules and the Fighter sim and diffs outcomes (block charges, combo progression, drop-through input, gravity arcs at fixed inputs).
